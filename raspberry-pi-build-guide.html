Build a Raspberry Pi delivery robot from scratch

Start with a Pi 4B, a blank microSD card, an ESP32, two independently driven wheels with signed position feedback, and a USB-connected LD19 LiDAR. Use ROS 2 Jazzy, SLAM Toolbox, and Nav2 for the robotics stack. Write the ESP32 firmware, the Pi’s drive bridge, and the delivery program yourself. The first goal is a delivery between two named points on one floor.

1. Prepare the Pi and create a workspace

Flash Ubuntu Server 24.04 ARM64 with Raspberry Pi Imager. Enable SSH at provisioning and use Ethernet for first boot if available. SSH lets you develop from your laptop with the Pi mounted on the chassis. Use the Pi 4’s recommended 3 A USB-C supply during bench work and leave motor power disconnected. This gives you a known power source while you debug the USB devices. Ubuntu flashing and SSH guide · Pi power specifications

Follow the Jazzy installation guide through adding the ROS apt repository. Then install the headless ROS runtime, mapping and navigation packages, and build tools. Run RViz on a Jazzy workstation if you want the Pi to stay headless. If RViz is remote, verify the two machines can discover each other on the same ROS domain. Jazzy apt setup

sudo apt install ros-jazzy-ros-base ros-jazzy-slam-toolbox \
  ros-jazzy-navigation2 ros-jazzy-nav2-bringup \
  python3-serial python3-colcon-common-extensions python3-rosdep
source /opt/ros/jazzy/setup.bash

Create a workspace such as ~/delivery_ws/src. Put your own ament_python package there, with entry points for drive_bridge and delivery. Keep the serial codec and differential-drive math as ordinary Python modules so you can test them on a laptop without hardware. Put the ESP32 firmware in a separate project and keep your launch files, robot measurements, and navigation parameters under version control. Creating a ROS 2 package

Plug the ESP32 and LiDAR adapter in one at a time and compare ls -l /dev/serial/by-path/ before and after. Record and label the physical ports so the drive bridge and the LiDAR driver open the right devices regardless of USB enumeration order. On Ubuntu, add your account to dialout if it lacks serial access, then reconnect to pick up the group membership.

2. Write the wheel firmware and Pi bridge

ESP32 firmware

Wire each motor driver according to its datasheet and verify voltage levels on the feedback and control signals. Start the firmware with outputs disabled. Decode each wheel’s Hall or encoder transitions into a signed cumulative count. With motor power off, rotate each wheel several full turns and measure counts per revolution and which sign corresponds to chassis-forward motion. Use changes in count over time to estimate wheel speed, then implement a PI loop per wheel that adjusts PWM toward its commanded speed.

Define a small USB protocol before writing the ROS node. At 115200 baud, newline-delimited JSON is easy to inspect on a bench. Start with five messages.

  • Hello starts a fresh, disarmed session. The reply includes a protocol version and a boot ID that changes on reset.
  • State reports the boot ID, sample time, both signed counts, measured speeds, arm state and faults.
  • Arm explicitly enables an otherwise healthy controller.
  • Speed carries two signed wheel targets, a session ID and a sequence number.
  • Stop zeros the drive output and disarms.

Give the ESP32 its own command watchdog so a frozen Pi or pulled cable cuts drive output. Use a bounded frame size, reject invalid or out-of-order targets, and refresh the watchdog only on accepted drive commands. After a timeout, fault or reconnect, require a fresh session and an explicit arm. Verify the physical power disconnect independently.

Pi drive bridge

First write a read-only serial tool that performs the handshake and prints encoder samples as you turn the wheels. Then make a ROS node that owns the serial port, publishes /odom as nav_msgs/Odometry, and broadcasts odom → base_link. Put base_link at the drive axle midpoint. Measure each wheel’s loaded radius and the center-to-center track width. With left and right travel distances dL and dR, use their mean for forward travel and (dR - dL) / track_width for heading change. Integrate the forward increment at the midpoint heading. Convert counts to distance using each wheel’s measured circumference and counts per revolution. On reset or a bad sample gap, rebaseline the counts and preserve the last pose.

For the command side, let v be forward velocity, w yaw rate, and b track width. The target ground speeds are v - w*b/2 for the left wheel and v + w*b/2 for the right. Divide by each wheel’s radius for rad/s. Scale both targets by the same factor if either exceeds the configured limit. Give the bridge a deadline on incoming commands and encoder feedback so it stops sending motion when either stream goes stale. Differential-drive kinematics

Bench check. A hand-pushed straight roll increases odometry x when starting at yaw zero. A left pivot increases yaw. With wheels secured off the ground, confirm each commanded direction and verify that stop, command loss, and USB loss cut drive output. Check that reconnect starts disarmed.

3. Map one floor with SLAM Toolbox

Build the manufacturer’s LD19 ROS 2 driver in your workspace with colcon. Use its LD19 launch example and set your actual serial path. If the vendor logger fails to compile on Ubuntu 24.04 with missing pthread_* declarations, include <pthread.h> in the logger source and rebuild. Source the workspace’s install/setup.bash in terminals that use the driver. Check that it publishes sensor_msgs/LaserScan on /scan with the frame ID you configured, for example base_laser. Look at a wall in RViz and confirm it appears on the correct side of the robot before tuning the mapper. LDROBOT driver and LD19 launch example

Publish the measured static transform base_link → base_laser with tf2_ros or a fixed joint in a URDF. The transform lets ROS place each laser ray relative to the chassis. Start SLAM Toolbox in online asynchronous mapping mode. Set its scan_topic to /scan and its frames to map, odom, and base_link. Your bridge supplies local odometry from the wheels. SLAM Toolbox compares scans and corrects accumulated drift through map → odom. SLAM Toolbox launch files and parameters

Push the robot slowly around a room with motor drive disabled and encoder feedback available. Revisit a wall you scanned early so the mapper can recognize the overlap. If the map shows doubled walls, check LiDAR orientation, wheel scale and yaw before changing SLAM parameters. Save the occupancy grid while the mapper is running. Keep the image and YAML together. The YAML records the resolution and origin Nav2 uses to place the map.

mkdir -p ~/maps
ros2 run nav2_map_server map_saver_cli -t /map -f ~/maps/floor-1

Mapping check. After a loop, revisited walls line up in RViz and the saved YAML points to an image that reflects the room you surveyed.

4. Localize on the saved map and run Nav2

Keep the LiDAR, wheel odometry and static sensor transform running. Stop the SLAM process and bring up Nav2 with your saved map and parameters. Map Server publishes the saved grid. AMCL compares live scans to that grid and takes ownership of map → odom. Set an approximate initial pose in RViz with 2D Pose Estimate, then hand-roll the chassis a short distance to verify the scan stays aligned with the map. AMCL parameters

Start your Nav2 YAML from the Jazzy example. Set AMCL’s base frame and Nav2’s robot base frames to base_link, and point the odometry consumers at /odom. Set the global costmap frame to map and the local costmap frame to odom. Configure the costmaps to observe /scan and give them a measured polygon footprint, including the overhang past the axle. Start with low speed and acceleration limits. The footprint matters because the corner of the chassis can sweep a much larger arc than the wheels during a turn. Jazzy parameter example · Footprint setup

Route the velocity output through Collision Monitor and give its output a dedicated topic that only it publishes. The bridge subscribes to that final topic. Set up a scan timeout and an obstacle stop zone, and explicitly match the velocity message type across the Nav2 components and your bridge. Check the live topic names, types, and publishers with ros2 topic info -v. If you add teleop, select between it and autonomous drive upstream of Collision Monitor so both use the same final path. Collision Monitor configuration

Once you’ve saved your edited parameters as ~/nav2.yaml, launch the localization and navigation nodes together. This gives both the same robot parameters and starts Map Server with the survey you just saved.

ros2 launch nav2_bringup bringup_launch.py \
  slam:=False map:="$HOME/maps/floor-1.yaml" params_file:="$HOME/nav2.yaml"

Navigation check. With drive disabled, set a short RViz goal and inspect the planned path and velocity output. After the raised-wheel tests, run a short supervised goal in a clear area with the physical disconnect within reach. Verify stopping on a controlled obstacle test, loss of scans, and loss of the velocity stream. Leave room for coasting.

5. Write the delivery program

Start with a CLI that takes a pickup and destination name. Keep names and poses in YAML. Each record should include a floor and the pose’s x, y, and yaw in that floor’s map frame. Record the poses in RViz once localization works so the program and map use the same coordinates.

  1. Validate both destinations and check that localization and Nav2 are ready.
  2. Send the pickup pose as a NavigateToPose action. Wait for the result without blocking cancellation or status updates.
  3. After a successful arrival, wait for a pickup confirmation, then send the drop-off pose.
  4. Report arrival only after the action succeeds. On failure or timeout, cancel the active goal and report which leg failed.

Use rclpy.action.ActionClient with nav2_msgs.action.NavigateToPose and the /navigate_to_pose action name. Fill the goal’s PoseStamped with frame map, the current ROS timestamp, x and y, and a yaw quaternion with z = sin(yaw/2) and w = cos(yaw/2). Call send_goal_async, check whether the goal was accepted, then call get_result_async on the goal handle. Use cancel_goal_async on timeout or user cancellation and wait for a terminal result before starting another leg. You can test the YAML lookup and job transitions on a laptop with a fake action server that accepts, rejects, or delays goals. Nav2 action interfaces

For multiple floors, add a state machine with explicit states for staging, supervised boarding, riding while stopped, supervised exit, and relocalization. Ask an operator to confirm the car, threshold and destination floor. After exit, load the destination map, reset AMCL near the known elevator exit, and wait for valid localization before resuming. Use a CLI or button for early confirmations. Recorded prompts or local text-to-speech can announce the same requests later. Exercise cancellations, timeouts and ambiguous confirmations in a simulated ride before putting the robot in a real elevator.
