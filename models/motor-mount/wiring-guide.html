PWM and direction interfaces

The pictured PWM input specifies 2.5–5 V. Start with 3.3 V hardware PWM at about 2 kHz, after confirming the input has no pull-up above 3.3 V. Set the onboard speed pot to minimum and verify zero duty with the wheels raised. Start with a 10 kΩ pull-down at each PWM input and verify that it actually holds zero drive when the ESP32 is off or resetting. If the controller overrides that bias, use a suitable interface with a verified default-off state before proceeding.

For each Rotation terminal, the diagram shows a switch to ground. A small NPN transistor such as a 2N3904 can act as that switch. Connect emitter → common GND, collector → Rotation, and ESP GPIO → 4.7 kΩ → base. Add 100 kΩ from base to emitter to keep it off during reset. Check the transistor’s actual pin order. GPIO high closes the ground switch. Test which wheel direction each state produces and switch only after the wheel stops. Leave Brake and Stop unwired for this bench setup.

Hall signal levels and direction

Measure all three Hall signals relative to controller signal ground with the harness connected and the wheel turned by hand. For 5 V signals within the buffer’s ratings, use one SN74LVC3G17 per wheel. Power each buffer from ESP32 3V3, share signal ground, and place a 100 nF bypass capacitor across each buffer supply. Connect HA/HB/HC to the buffer inputs and its outputs to the assigned GPIOs. Configure those GPIOs as inputs. The drivers supply their own Hall harnesses. Keep the Hall 5 V wires off the ESP32 supply.

Decode the order of valid three-bit Hall transitions to count rotation in both directions. With drive disabled, mark each wheel and turn it through several full revolutions. Use the measured transitions per revolution, and set each wheel’s sign so rolling the robot forward gives positive counts on both sides.

Power and motor harnesses

  • On each controller, connect the battery distribution branch to VCC and power GND with the polarity verified. Verify the pack’s full-charge voltage against the controller and converter ratings. This prototype layout uses the existing battery/BMS path. Its cutoff ratings and protection of the new wiring remain unverified.
  • Use a separate branch for the DC–DC converter input. Power the Pi through USB-C with a regulated 5 V supply capable of 3 A. Check the output and polarity before connecting the Pi. A normal Pi wall supply is convenient for initial bench tests.
  • Feed the ESP32 from the Pi’s USB data cable. Leave the ESP32’s 5V pad and the controllers’ external 5 V out leads disconnected from that supply.
  • Connect each motor’s three thick phase leads to its own controller’s MA/MB/MC. Connect its Hall harness to the separate controller header marked GND, HA, HB, HC, 5 V. Match phase and Hall order using the motor and controller pinouts. Wire colours are only clues. Branch HA/HB/HC to the ESP32 buffers as shown above.

Connect the Pi peripherals

Connect the lidar via its USB adapter, the microphone via USB, and the powered speaker via the Pi’s 3.5 mm audio jack if using the previously discussed speaker. Use a data-capable USB cable for the ESP32.

For the optional BMP390 with a Qwiic/STEMMA QT socket, use a 4-pin JST-SH to female DuPont cable. The sockets go directly on the Pi header.

First power-up

  1. Leave motor power disconnected. Enable USB CDC On Boot in the ESP32 Arduino configuration and choose Hardware CDC and JTAG when available. Connect Pi USB-A to ESP32 USB-C. The board’s TX/RX pads can stay unused.
  2. Check the Pi sees a serial device with ls /dev/ttyACM*. Use newline-delimited JSON. A 115200 setting can be used in the client, but the native USB connection does not run at that UART baud rate.
  3. Secure the chassis with wheels clear. Confirm the driver remains stopped with the ESP32 unplugged, powering up and resetting. With drive disabled, verify Hall voltage and signed counts by turning each wheel by hand in both directions. Then test one wheel at low duty. Use a current-limited supply for initial motor tests when available.
  4. With the wheels still raised, unplug USB during a low-speed test. Verify the drive output goes to zero. In firmware, default to stopped, stop on stale commands (start with 250 ms), and require a fresh command session after reconnecting.
